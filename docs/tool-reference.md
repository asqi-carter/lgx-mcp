# Tool reference

The core build registers 29 tools; an SDK build adds the 13 tools of the
[Logix Designer SDK lane](../README.md#logix-designer-sdk-lane), 42 in all. Every tool's docstring states its gate
behavior explicitly (project rule). `project` is implicit everywhere: tools act
on whichever project the current session has open via `logix_open_project`.

Tools are grouped the same way as the [README](../README.md#tools): read and
analyze, live writes, setup, then the two SDK-lane groups (present only in an SDK
build). Every tool has exactly one row.

**Gates / flags column key:**
- **—** available with no flag
- **`LIVE_WRITES`** — refused unless `LGX_ENABLE_LIVE_WRITES=1`
- **`confirm=true`** / **`confirmedByUser=true`** — an explicit argument on the call; it may only be passed after the user has explicitly approved the change, and the server cannot verify that approval (see the [safety model](safety-model.md))
- **`STUDIO_AUTOMATION`** — SDK lane: refused unless `LGX_ENABLE_STUDIO_AUTOMATION=1`
- **`LIVE_FINALIZE`** — SDK lane: refused unless `LGX_ENABLE_LIVE_FINALIZE=1`
- **Gate-enforced** — every written tag is checked against the write-gate policy derived from the open project; a denied tag is rejected with `kind: "WriteDenied"` and a provenance string

"What it can change" names the most the tool can alter. **Nothing** means the
tool is read-only: it never writes a tag, a file, or the controller.

Static analysis needs no controller. Live reads need a `logix_connect` session.

| `logix_trace_origin` | Traces where a tag's value comes from, backward through the open project. Writers are found with the same write classification the write gate uses, so the trace and the gate agree on what writes a tag: RLL instructions, ST assignments and calls, FBD output references, SFC actions, aliases (`AliasFor`), AOI output and in-out parameters, MSG destinations, output and in-out program parameters and parameter connections. Each write node gives the program, routine and rung (or ST line), the instruction, the source operands, the gating conditions (rung contacts and comparisons, or the enclosing ST `IF`) and any literal; `OTE`, `OTL`, `OTU`, `CLR` and `RES` carry the implicit values `1`, `latch`, `unlatch`, `0` and `reset`. The trace follows each source and condition tag in turn and stops at a literal, a tag nothing writes (an entry in `externalInputs`, with a `kind` of `io`, `consumed`, `constant`, `parameter` or `unwritten`), `maxDepth` (default 6, at most 50; the tags left unfollowed are in `depthLimited`) or a cycle (recorded in `cycles`, never looped). `tag` may be a member path: `Source9.AirBlow` is one reference and does not pull in the writers of `Source1.AirBlow` or `Source9.Other`. A bare name that is a program tag in exactly one program resolves to it; otherwise use `Program:<program>.<tag>`. `focus` limits the trace to writes made in one program. `format`: `text` (default; an indented tree), `json` (`nodes`, `edges`, `externalInputs`, `literals`, `gaps`, `cycles`), `mermaid` (a flowchart with one box per writing rung) or `all`. Reads the opened or uploaded project, not the live controller's running state; `source` says which image: `project-file`, `accepted-image` or `session-image`. With `includePending` (default true on SDK-online sessions) it traces the session's controller image with staged, pending and tested rungs applied (`session-image`); with `includePending: false` it traces accepted logic only and lists the rungs left out under `pendingWriters`, each with a `state` of `staged` (held on the workstation, not yet sent to the controller), `pending` or `tested` (executing on the controller). A stale image is flagged with `imageStale: true` (the hint is to reconnect with `logix_connect`). | Nothing | — |

| `logix_gate_report` | Derives the write-gate policy fresh from the open project and returns every grant and deny with full provenance. Also reports `policySource` (`project-file`), `sourcePath`, and `enforcedBySession` (true only when the report is the exact policy the active session's write gate enforces). For a partial export (`partialExport: true` on `logix_open_project`) no gate can be derived from the file. Without `LGX_WRITE_ALLOWLIST` the report is `hypothetical`, never `enforced`, and states why. With it, the report is `enforced` with `policySource: "allowlist+partial-export-denies"`: grants come only from the allowlist, each allowlist entry is listed as a grant (or a deny) with any deny or range the partial file proves, and file tags the allowlist does not name are not listed. | Nothing | — |
| `logix_verify_interlock` | Static structural proof: does every rung that writes `outputTag` also carry `conditionTag` as an XIC/XIO contact? Returns every write-path rung with `conditionPresent` per rung, not just an overall verdict. `result` is `verified` (every path to every write of `outputTag` passes through the condition contact, directly or through a chain), `bypassed` (the contact is on some paths but a branch reaches the output without it; the offending paths are in `bypassPaths` on the rung) or `unverified` (not verified: a writing rung lacks the condition, an intermediate bit has an unguarded writer, or a rung could not be parsed). A rung not directly guarded can be guarded through intermediate bits (status `chained`): `via` lists the bits, nearest the output first, and `chain` shows the path (e.g. `Drive <- StartBit <- Cond`). The chain depth limit is 3 intermediate bits. A proving chain deeper than 3 is not verified and carries `reason: "depth-limit"` (with `via` and `chain` showing the too-deep chain); `reason: "unguarded-writer"` means an intermediate bit has a writer the condition does not guard, listed in `unguardedWriters`. `reason: "condition-after-output"` means the condition contact sits after the output instruction on the rung, so it gates nothing (status `condition-after-output`, not `bypassed`); `reason: "xio-of-guarded-bit"` means the output is gated by `XIO` of a bit that is itself interlocked (XIO passes when the bit is false, so it does not require the condition). An unguarded `OTU` of the output or of a chain bit only clears it, so it does not block `verified`: the note reads "unlatch writer not interlocked (unlatching is safe-direction)" and the OTU rung is listed in `unguardedWriters`. A depth-limit result lists only the chain, not unrelated writers. Rungs that could not be parsed are listed in `unparsedRungs`; one that mentions `outputTag` blocks `verified` because it may write the tag unguarded. Structural proof only, not runtime verification. | Nothing | — |

### `logix_diagnose`: `status` and `forces`

**`status`** is the ListIdentity status word (`identityStatus`) decoded with
Rockwell's published bit table. It also carries `deviceStatusBits` (the raw
bits 7..4 as four binary digits) and a `source` field citing the table.

| Bits | Field | Values |
|---|---|---|
| 7..4 | `deviceStatus` | `0001` flashUpdateInProgress, `0100` flashBad, `0101` faultedModes, `0110` run, `0111` program, anything else `reserved` |
| 11..8 | `faults` (list, empty when none) | bit 8 recoverableMinor, bit 9 unrecoverableMinor, bit 10 recoverableMajor, bit 11 unrecoverableMajor |
| 13..12 | `keyswitch` | `01` run, `10` program, `11` remote, `00` unknown |
| 15..14 | `modeFlag` | `00` none, `01` changingModes, `10` debugMode, `11` unknown |

Source of the table (also returned in `status.source`): Rockwell Logix
Designer help, "Access the ControllerDevice object", Status.

**`forces`** always has `reported: false`. Force status is not readable over
CIP by an outside client, so `logix_diagnose` never says whether forces are
on or off, and an absent force is never implied. It returns `reason` (why it
is not reported) and `howToCheck` (how to find out):

> Look at the Forces indicator in Studio 5000 (online), or add logic: GSV Module ForceStatus into a DINT tag (bit 0 = forces installed, bit 1 = forces enabled), then read that tag with `logix_read`.

When `status.modeFlag` is `debugMode`, `forces` also carries a `note`. It
says that Rockwell's help does not state whether debug mode means forces are
on, so check in Studio. `debugMode` is reported as such and is not
interpreted as forces.

## Live writes

These change tag values, controller mode, or files. Gates are enforced on
every call. See [`safety-model.md`](safety-model.md).

| Tool | What it does | What it can change | Gates / flags |
|---|---|---|---|
| `logix_write` | Write a value to a tag through the active session. The value must be of the tag's exact declared type; no silent coercion — a mismatch returns `kind=TypeMismatch`, an untypeable tag `kind=TypeUnknown`. A denied tag (including any whose External Access is not `Read/Write`) is rejected with `kind: "WriteDenied"` and a provenance string; an out-of-bounds value on a granted, range-annotated tag is also rejected. With `LGX_AUDIT_FAIL_CLOSED` set to `1`, `true` or `yes`, a write is refused with `AuditUnavailable` when `audit.jsonl` cannot be opened for append; this check runs before the write is sent and is not a transaction, so an append that fails after the write is reported but the write is not rolled back. | One tag's value | Gate-enforced. Live (non-virtual, non-`l5x`) targets: `LIVE_WRITES` |
| `logix_controller_mode` | Read the controller's current mode, or request a change (Program/Run/Test). On a live controller a mode change is **not applied** in this release and returns `kind: "ModeChangeNotApplied"`; change the mode in Studio 5000 or at the keyswitch. | Nothing on a live controller in this release (mode change is refused); virtual/emulated sessions can change mode | Mode changes on a physical controller: `LIVE_WRITES` + `confirm=true` |
| `logix_import_datatype` | Offline-only datatype import (not a live write). Accepts `acdPath` (the source project path, used only for lock-checking), `datatypeName`, and either `l5xPath` (a `Use="Target"` L5X export) or `members` (an ordered member list the tool renders to L5X, including dependent types). `saveAs` is required, must differ from `acdPath`, and must end in `.L5X` in this build (`kind: "InvalidSavePath"`; an `.ACD` `saveAs` is refused with `SdkRequired`). `dryRun` defaults to `true` (returns the fragment without writing). Creates the type when it does not exist, otherwise changes it per `collision` (a dry run previews a new type with `willCreate: true`). A real run is verified by re-exporting the type before the file is moved into place; if the members differ it returns `ImportNotApplied` and writes nothing, and `collision: Cancel` on an existing type returns `ImportCancelledOnCollision`. The SDK's import messages are returned as `sdkMessages`. An existing `saveAs` is refused with `TargetExists` unless `overwrite=true`; output is built in a temp file and moved into place atomically, and a failed import removes only that temp file. Without the SDK the fragment is not verified (`verified` absent) and `note` says no project import was performed; with the SDK but no re-export reader `verified` is `null` and `note` says the import could not be verified. | A new `.L5X` file at `saveAs` (never the source file, never the controller) | Real write (`dryRun=false`): `confirm=true` |

### Resource: `lgx://sdk/capabilities`

An MCP resource (JSON) that reports what the Logix Designer SDK can do on this machine and session: the build check, finalize edits, rung delete, program export with `TestEdits`, online tag write, upload, the Designer version and the SDK package version. Each entry is `available`, `unavailable` or `unknown`, with its `source` (`version-rule`, `install` or `observed`). It needs no session: without one it reports what the install shows. The same table appears as `capabilities` in `logix_connect` (SDK backend) and `logix_doctor`. A tool that needs an unavailable capability is refused with `kind: "SdkCapabilityUnavailable"`.

## SDK lane: rung edits, build and test

Present only in an SDK build, and they work only in an SDK session
(`logix_connect` with `backend="sdk"`); without one they return
`NoActiveSession`. Each tool also needs the Logix Designer SDK build and a
licensed Studio 5000 or FactoryTalk Logix Echo install on the host. See the
[README](../README.md#logix-designer-sdk-lane) for requirements and install.

| Tool | What it does | What it can change | Gates / flags |
|---|---|---|---|
| `logix_export_rungs` | Exports the current rungs at an SDK XPath (`xPath`, for example `Controller/Programs/Program[@Name='MainProgram']/Routines/Routine[@Name='MainRoutine']`) as an L5X fragment. Returns `status: "ok"`, `xPath` and `l5x`. The `l5x` is the input `logix_propose_rung_edit` takes as `l5xFragment`, unchanged. When the export holds project-authored text (rung comments, tag descriptions), the result adds `untrustedContent` and a `notice`; the `l5x` itself is never altered. Returns a structured error when no project is loaded or the export fails. | Nothing | — |
| `logix_propose_rung_edit` | Imports rungs (`rungs`, `tags` or an `l5xFragment`) at `insertPosition` in the routine named by `routineXPath`, replacing `replaceCount` existing rungs (`0` is a pure insert). Positions count the rungs you see in `logix_get_routine` (originals not replaced, plus staged rungs): `insertPosition` may be 0..N where N appends, and `insertPosition + replaceCount` must not exceed N; otherwise the call is refused (`InsertPositionOutOfRange`, `ReplaceCountOutOfRange`) and nothing is staged. Where the edit lands depends on `target`. `workstation` (default) only stages it in the server's in-memory project image; staged edits accumulate and reach no controller. `controller` publishes the staged set as a pending edit that is not executing; one publish per accept or cancel cycle, and a pending zone blocks every further import into that program until it is accepted or cancelled. `live` publishes and finalizes in one call, so the rungs execute at once, and each success carries an `undo` block to revert them (`rungs: []` with `replaceCount > 0` deletes rungs; `expectedRungText` is required when `replaceCount > 0`, and a changed rung is refused with `StaleTarget`). `offline=true` edits the `.L5X` file on disk without contacting a controller and returns `status: "saved-to-file"`. Tags the publish declares are created on the controller at once and stay when the rungs are cancelled or undone; they are External Access Read Only, and an edit that changes an existing tag's External Access is refused (`ExternalAccessChangeRefused`). Each `tags[]` declaration is checked against the project's existing tags at stage and at publish: a tag that already exists with the same data type is left out of the import and listed in `reusedTags` (`name`, `dataType`; "already exists; declaration ignored"); an existing tag with a different type is refused with `TagTypeConflict` (`tag`, `existingType`, `declaredType`); a `dataType` that is neither atomic nor a type in the project is refused at stage with `UnknownDataType` (`tag`, `dataType`; the hint names `logix_list_datatypes`). Nothing is staged or published on a refusal. The gate analysis attached to each response informs the engineer; the engineer decides. | `workstation`: the in-memory project only. `controller`: pending rungs and any new tags on the controller. `live`: the running logic and any new tags. `offline=true`: the `.L5X` file | Gate-enforced on every tag the edit references. `controller` and `live`: `LIVE_WRITES`. `controller` also `confirmedByUser=true` unless `LGX_PUBLISH_MODE=auto`. `live` also `LIVE_FINALIZE` and `confirmedByUser=true` (even with `LGX_PUBLISH_MODE=auto`). Refusals: `CapabilityDisabled`, `ConfirmationRequired`, `StagedRungsPresent`, `PendingZoneExists`, `TagTypeConflict`, `UnknownDataType` |

## SDK lane: Studio automation

Each of these five tools drives the Studio 5000 Logix Designer window on the
engineer's interactive desktop by posting Studio's own menu command, because the
SDK has no call for these steps. They are experimental. They send no keystrokes
and no mouse clicks, and they work only with the program the engineer has open
in Studio. All five:

- are refused with `CapabilityDisabled` unless `LGX_ENABLE_STUDIO_AUTOMATION=1`
  is set; accept, test, untest and assemble also need `LGX_ENABLE_LIVE_WRITES=1`,
  because they change the running controller;
- are refused unless `confirm=true`, which you pass only with the engineer's
  go-ahead (the server cannot verify it);
- refuse when Studio 5000 is not installed on the host, when Studio is in another
  session or elevated, and when the routine has nothing pending;
- read `logix_pending_edits` afterward and report both the before and after
  snapshots with screenshot paths, so success is never claimed on the gesture alone.

| Tool | What it does | What it can change | Gates / flags |
|---|---|---|---|
| `logix_accept_pending_edits` | Accepts the routine's pending edits and finishes the zone in one step (Studio's Assemble Accepted Program Edits command). Returns ok only when the routine afterward has nothing pending; if the gesture succeeded but the routine is still pending, it returns an error naming both states. A pending zone this server did not publish (another session or Studio did) is refused with `ForeignPendingZone` (`program`, `routines`, `publishedByThisServer: false`) before any Studio command; review it in `logix_pending_edits` and pass `acceptForeign=true` to finalize it anyway (the result then carries `foreign: true`), or cancel it. | The running controller: the pending rungs begin to execute | `STUDIO_AUTOMATION` + `LIVE_WRITES` + `confirm=true` |
| `logix_test_pending_edits` | Tests the accepted edits: the new logic executes on the running controller and the original is kept. Needs a pending, untested zone; an already tested one is refused with `AlreadyTested`. Returns ok only when the export afterward shows the zone as `tested` (`TestStateNotConfirmed` otherwise). A pending zone this server did not publish (another session or Studio did) is refused with `ForeignPendingZone` (`program`, `routines`, `publishedByThisServer: false`) before any Studio command; review it in `logix_pending_edits` and pass `acceptForeign=true` to test it anyway (the result then carries `foreign: true`), or cancel it. `dialogWarnings` carries Studio's own warnings word for word; read them. | The running controller: the new logic executes alongside the kept original | `STUDIO_AUTOMATION` + `LIVE_WRITES` + `confirm=true` |
| `logix_untest_pending_edits` | Puts the original logic back after a test. Needs a tested zone; an untested one is refused with `NotTested`. Returns ok only when the zone afterward is `untested` (`UntestStateNotConfirmed` otherwise). The zone stays pending: follow with `logix_cancel_pending_edits` to discard it. | The running controller: the new logic stops executing | `STUDIO_AUTOMATION` + `LIVE_WRITES` + `confirm=true` |
| `logix_assemble_pending_edits` | Assembles a tested zone, finalizing its rung edits. Irreversible: neither untest nor cancel can undo it. Needs a tested zone (`NotTested` otherwise); `logix_accept_pending_edits` finalizes in one step. Returns ok only when the routine afterward has nothing pending. A pending zone this server did not publish (another session or Studio did) is refused with `ForeignPendingZone` (`program`, `routines`, `publishedByThisServer: false`) before any Studio command; review it in `logix_pending_edits` and pass `acceptForeign=true` to assemble it anyway (the result then carries `foreign: true`), or cancel it. | The running controller: the tested rungs become the program, permanently | `STUDIO_AUTOMATION` + `LIVE_WRITES` + `confirm=true` |
| `logix_cancel_pending_edits` | Cancels the pending or accepted edits through Studio's Cancel Accepted Program Edits command, discarding the rungs. A tested zone is refused with `ZoneTested`: call `logix_untest_pending_edits` first. Tags created by an earlier publish stay on the controller. Cancel is never refused as a `ForeignPendingZone`: when this server did not publish the zone it proceeds and the result carries `foreign: true`. | The controller's pending rung edits (discarded) | `STUDIO_AUTOMATION` + `confirm=true` (no `LIVE_WRITES` needed) |

## Environment variables

The [README](../README.md#environment-variables) lists all 14 environment
variables; the ones marked SDK lane act only in an SDK build. The ones most
relevant to the tools above:

| Variable | Default | Effect |
|---|---|---|
| `LGX_ENABLE_LIVE_WRITES` | off | Enables live tag writes and controller mode requests (`LIVE_WRITES` above). |
| `LGX_WRITE_ALLOWLIST` | unset | Site allowlist of writable tags. With no project open it is the only check on a live CIP session; with a full export it only narrows the derived gate; with a partial export it is the only source of grants and the partial file's denies and ranges still apply. |
| `LGX_TAG_ROUTE` | `auto` | Tag route in an SDK online session: `auto` (CIP when it connects to the same controller, else SDK), `cip` (CIP only; `TagRouteUnavailable` when it cannot connect) or `sdk`. Results carry `route`; `logix_doctor` shows the active route and why. SDK lane only. |
| `LGX_AUDIT_FAIL_CLOSED` | off | Set to `1`, `true` or `yes` (case-insensitive) to check, before a `logix_write` is sent, that `audit.jsonl` can be opened for append; if it cannot, the write is refused with `kind: "AuditUnavailable"` and nothing is sent. This is a pre-flight check, not a transaction: an append that fails after the write is reported on stderr and by `logix_doctor` (`auditWriteFailures`) but the write is not rolled back. Off by default. |
| `LGX_AUDIT_MAX_MB` | `50` | Rotate `audit.jsonl` before an append would take it past this many megabytes. `0` disables rotation; unset, unparsable or negative values use the default. |
| `LGX_AUDIT_KEEP` | `5` | Number of rotated audit files kept (`audit.1.jsonl` …). Minimum `1`; the oldest is deleted. |
| `LGX_ENABLE_STUDIO_AUTOMATION` | off | Enables the five Studio automation tools (`STUDIO_AUTOMATION` above). Each call also needs `confirm=true`. SDK lane. |
| `LGX_ENABLE_LIVE_FINALIZE` | off | Enables `logix_propose_rung_edit` with `target="live"` (`LIVE_FINALIZE` above). Each call also needs `confirmedByUser=true` and `LGX_ENABLE_LIVE_WRITES=1`. SDK lane. |
| `LGX_PUBLISH_MODE` | `confirm` | `auto` lets `logix_propose_rung_edit` publish with `target="controller"` without `confirmedByUser=true`; anything else means `confirm`. It does not relax `target="live"`. SDK lane. |
